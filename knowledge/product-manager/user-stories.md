# User stories

- A user story is "the smallest unit of work in an Agile framework", written from the user's point of view. It is an informal, short description of an outcome the user wants. Details get added later, once the team agrees on them.
- Template: **"As a [user], I want [goal] so that [reason]."** The structure is optional, but it helps the team define when a story is done.
- Base each story on a specific persona. If there are several distinct users, write a separate story for each. For a larger process, write one story per step.
- Gather the need in the users' own words, for example from their feedback.
- Keep each story small enough to finish in one sprint. Split bigger work, or treat it as an **epic**. Epics are broken into stories, and several epics make up an **initiative**.
- Leave implementation details out. Focus on the user's goal.
- **Three C's:** Card (the written story), Conversation (discussion that clarifies details), Confirmation (acceptance criteria that define when it is complete).
- A story is generally done when the user can complete the task it describes. The team should say explicitly what "done" means.
- Stories are usually written by a product owner or product manager and then reviewed by the team. Teams size them with t-shirt sizes, Fibonacci numbers or planning poker.
- The source does not mention INVEST.

## HelpMate example
"As a nervous first-time user on a phone, I want to hear the steps read aloud so that I can follow them while I tap."
